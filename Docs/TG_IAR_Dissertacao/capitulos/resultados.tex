\section{Estrutura do Pedestal}\label{sec:estrutura}
O protótipo físico será baseado no mecanismo apresentado na Figura~\ref{fig:pedestal}. As peças utilizadas no modelo 3D do pedestal empregam componentes COTS (\textit{Commercial Off-The-Shelf}, ou seja, hardware comercial pronto para uso). Dessa forma, a geometria e os elementos foram projetados para utilizar materiais de fácil acesso no comércio local e em lojas de construção.

As polias utilizadas são do tipo GT2, de 20 e 40 dentes (vide Figura \ref{fig:polias_cinto}), associadas a uma correia dentada de \SI{10}{\milli\meter} de largura e \SI{200}{\milli\meter} de comprimento perimetral, o que estabelece uma distância entre centros conhecida.
Esses elementos, assim como os motores de passo NEMA 17, são amplamente empregados na fabricação de impressoras 3D.

Para o acionamento dos motores, foram adotados os drivers DRV8825, comumente encontrados em lojas de eletrônica. 
O microcontrolador ESP32 e o display LCD seguem a mesma facilidade de aquisição do restante dos componentes eletrônicos.

A estrutura do poste foi dimensionada para utilizar um pontalete de madeira de \SI{7,5}{\centi\meter} $\times$ \SI{7,5}{\centi\meter}, enquanto a base foi projetada para tábuas de \SI{0,9}{\centi\meter} $\times$ \SI{9,5}{\centi\meter}. O fio de cobre maciço usado para a confecção da antena foi obtido a partir do desmembramento de um cabo de aterramento de 7 vias, no qual cada condutor individual possui bitola \SI{10}{AWG}.

A tela de alumínio utilizada como plano de terra foi adaptada de uma tela mosquiteira de alumínio de \SI{1}{\square\meter}. Já a chapa metálica complementar do plano de terra foi produzida a partir de um rufo para telhado.

O cobre foi inserido no suporte helicoidal com um comprimento de sobra para ajustes futuros. Além disso, foi mantida uma região de cobre após o conector SMA para corrigir a impedância entre a antena helicoidal, com impedância característica por volta de \SI{140}{\ohm} \cite{balanis2016}, e aproximá-la da impedância na linha do amplificador (de \SI{50}{\ohm}). O casamento de impedância é importante para permitir a máxima transferência de potência do sinal recebido pela antena \cite{balanis2016}.

\section[Filtro Alfa Beta Gama]{Levantamento dos Parâmetros do Filtro $\alpha$-$\beta$-$\gamma$}

Conforme apresentado na Seção \ref{sec:implementacao_filtro}, os parâmetros iniciais do filtro foram obtidos a partir de dados de rastreamento de diversos satélites de órbita baixa (LEO) utilizando um servidor ligado ao aplicativo SatDump.
O método escolhido para a captura de amostras foi o de programar o software de rastreio para obter diversas passagens de constelações de satélites de órbita baixa, em diversas altitudes e condições reais nas quais o mecanismo irá operar.
As constelações utilizadas foram a Meteor (satélites meteorológicos), OneWeb (internet banda larga), Capella (radares de arbetura sintética, conhecidos como Synthetic-aperture radar ou SAR), ICEYE (SAR), Black Kite (internet das coisas, Internet of Things ou IoT), e Sentinel (monitoramento de desastres).

Após a seleção dos satélites de interesse, foi feito um script em Python capaz de simular a conexão entre o SatDump e o rotor, recebendo e enviando dados para o programa.
Esse script recebia os parâmetros e os salvava em um arquivo de extensão ".txt" para uma pasta com as demais capturas. O programa foi executado durante diferentes horários ao longo de dois meses, acumulando um total de 330 amostras.
Em seguida, aplicou-se um método computacional de varredura sistemática (\textit{grid search}) para a otimização dos coeficientes, variando-se os parâmetros em incrementos de $0,1$ para $\alpha$ e $\beta$, e de $0,01$ para $\gamma$, respeitando os limites de estabilidade definidos pelo Critério de Jury (Seção~\ref{sec:estimation}).

O desempenho do filtro para cada combinação de parâmetros foi avaliado ao longo das passagens dos satélites por meio do Erro Quadrático Médio (EQM, ou RMS em inglês). A partir desses resultados, geraram-se superfícies tridimensionais correlacionando os coeficientes ao menor erro obtido.
Essa representação permitiu identificar uma região operacional ótima, na qual o filtro $\alpha-\beta-\gamma$ apresenta convergência satisfatória para a maioria das trajetórias orbitais analisadas.
A região em questão se encontra na região de valores $\gamma$ baixos, possuindo os menores erros entre os valores preditos e os reais.
A partir dos valores obtidos, é possível verificar a região com menor erro RMS para cada elemento. Os valores para azimute foram de $\alpha = 0{,}9333$, $\beta = 0{,}0333$, e $\gamma = 0$, enquanto os valores para a elevação foram $\alpha = 0{,}9333$, $\beta = 0{,}2$, e $\gamma = 0$.

Como a aproximação anterior ocorreu de forma grosseira, dividindo os valores dentro de determinados quadrantes, foi desenvolvido um algoritmo para rastrear o melhor ponto a partir da melhor estimativa dada pelo método anterior.
Esse segundo algoritmo funciona iniciando a sua pesquisa a partir do melhor ponto predito, alternando os parâmetros do filtro a partir de um determinado passo estimado como metade do passo que gerou os quadrantes anteriores.
O código então alterna cada filtro entre o melhor parâmetro, o melhor parâmetro somado com o passo, e o melhor parâmetro subtraindo o passo.
Com os filtros configurados, todas as amostras de passagem são novamente calculadas e o erro RMS é calculado para cada uma.
O programa seleciona o filtro com o menor erro e repete o processo novamente. Quando o algoritmo não encontra um parâmetro menor que o parâmetro inicial, ele divide o passo utilizado pela metade e reinicia o cálculo.
Quando o algoritmo repete os mesmos parâmetros de filtro um determinado número de vezes (para o caso do projeto, 15 vezes), o programa é encerrado e os valores calculados são determinados como os valores ótimos para o filtro.

Os valores obtidos continham 16 casas decimais, porém, nesse nível de precisão, erros de arredondamento em ponto flutuante acabam interferindo no resultado. Além disso, os parãmetros do filtro serão arredondados para baixo a fim de evitar instabilidades no sistema.
Dessa forma, arredondando para três algarismos após a vírgula, foram obtidos $\alpha = 0{,}937$, $\beta = 0{,}298$, e $\gamma = 0.120$ para o azimute, e $\alpha = 1{,}071$, $\beta = 0{,}253$, e $\gamma = 0.122$ para a elevação.
É importante ressaltar que o $\alpha$ para a elevação está selecionado como sendo maior que 1. Esse valor não é usual, já que india uma estimação de predição que estima um valor maior que a da amplitude do erro. Porém, como o algoritmo convergiu a este valor, os parâmetros embarcados serão os indicados anteriormente.

Isso mostra que o sitema é subamortecido.
O mesmo fenômeno é observado para uma passagem próxima de zênite, na qual o azimute sofre uma variação brusca, fazendo ocorrer uma oscilação quando há uma diminuição na taixa de crescimento do ângulo.
Uma solução para esse fenômeno seria alterar os parâmetros do filtro, fazendo com que esse tenha uma banda passante menor, aumentando o amortecimento do sistema para altas frequências.
Outra solução pode ser incluir no algoritmo uma forma de detectar a diferença entre a posição predita e a posição real, reiniciando os parâmetros de predição do filtro quando essa diferença ultrapassar determinado valor.

\section{Simulação do Mecanismo}\label{sec:MuJoCo}

    \centering

O MuJoCo (Multi-Joint dynamics with Contact) é um dos simuladores de física de corpo rígido desenvolvido pela empresa Roboti LLC e disponibilizado gratuitamente pela Google Deep Mind.
Esse simulador tem o intuito de simular de forma fidedigna a interação entre os mecanismos desenvolvidos e o ambiente.

O software foi utilizado para simular o protótipo. Para isso, a ferramenta de nome onshape-to-robot \cite{onshapetorobot2020} foi aplicada para auxiliar à tradução do modelo CAD desenvolvido para o modelo na plataforma.
Após a conversão, o resultado foi um modelo capaz de ser simulado fisicamente no MuJoCo, conforme visto na Figura \ref{fig:modelo_mujoco}.

Com o modelo do projeto convertido, é possível utilizar a biblioteca do MuJoCo para Python a fim de controlar os graus de liberdade do modelo (sendo esses, azimute e elevação).
Esse simulador possui uma conexão com o software de rastreio SatDump, recebendo os dados de posição e inserindo-os ao filtro $\alpha-\beta-\gamma$.
O filtro foi diretamente adaptado do programa escrito em C do ESP32 para o Python e seu resultado foi enviado ao MuJoCo.
A posição predita pelo filtro é enviada ao simulador, que representa a posição do sistema a cada determinado momento.
A fim de verificar o funcionamento do filtro, foi desenvolvido um gráfico que mostra o funcionamento do sistema em tempo real. Esse gráfico possui uma linha indicando a posição do satélite e a posição predita pelo filtro, e pode ser visto na Figura \ref{fig:simul_abg}.
A linha vermelha indica a posição real do satélite enviada pelo SatDump, enquanto a linha azul indica a posição das juntas do mecanismo simulado. Para a finalidade de otimização do desenho do gráfico, foram mantidos somente os últimos 300 pontos dos dois desenhos.
Como o filtro gera uma grande quantidade de pontos intermediários, a linha azul possui uma maior densidade de pontos e um comprimento menor. O tempo que compõe o eixo X é a quantidade de segundos desde o início da captura. 
No gráfico, é possível perceber a correção dos parâmetros do filtro marcadas pelos "dentes de serra" na curva azul, mostrando que o sistema está estimando a trajetória do satélite em tempo real e corrigindo as estimativas de posição, velocidade e aceleração.
As últimas amostras do filtro demonstram que o sistema conseguiu estabelecer o rastreio corretamente, necessitando de poucas correções para se manter na trajetória correta.

O resultado da simulação pode ser visto nos Apêndices \ref{cap:apendice_umbra} e \ref{cap:apendice_troca_sat}.
Foi possível perceber que o sistema se comportou de maneira esperada, se mantendo sob controle durante todo o rastreio (demonstrado na totalidade do vídeo do Apêndice \ref{cap:apendice_umbra}).
O filtro também conseguiu se estabilizar após uma troca de satélite alvo, independentemente de sua posição, órbita, ou velocidade.

Entretanto, alguns comportamentos inesperados ocorreram com a simulação do sistema.
O primeiro e mais crítico é o que, na rotina de retorno à posição inicial, o sistema acaba acelerando demasiadamente.
No sistema físico, esse comportamento poderá causar um grande estresse no sistema, causando dano estrutural ao protótipo.
O retorno à posição inicial ocorre sempre que o sistema para de receber informação por um período maior que 30 segundos (6:55 do Apêndice \ref{cap:apendice_troca_sat}) ou no final de um rastreio (10:56 do Apêndice \ref{cap:apendice_troca_sat}), permitindo o sistema desenrolar os cabos e se preparar para uma nova captura.
Uma solução que poderá ser implementada ao sistema final é possuir uma velocidade máxima dos motores para se movimentar entre alvos.
Isso garantirá que o sistema não virá a sofrer danos estruturais durante sua operação.

Uma segunda questão que acabou auxiliando o sistema simulado é que, como visto nas figuras \ref{fig:passagens_diversas} e \ref{subfig:passagem_zenite}, o filtro possui grandes sobressinais quando o sistema muda seu alvo abruptamente.
Entretanto, como visto principalmente no vídeo de troca de alvos do Apêndice \ref{cap:apendice_troca_sat}, a inércia do sistema impede o desalinhamento da antena, fazendo com que o sobressinal não seja realmente aplicado ao modelo.
Apesar desse efeito, a oscilação ainda se mantém, fazendo com que o sistema divirja da posição desejada (como pode ser visto aos 1:55, 5:18, e 5:52 minutos do vídeo). Após um determinado período de tempo, o sistema retorna a se estabilizar e seguir a posição do satélite.
Esse problema parece ser causado pela característica do sistema de tentar manter a predição anterior. Então, até todos os fatores se corrigirem para a nova trajetória, ocorre uma oscilação claramente visível na posição da antena.
A solução para esse caso pode ser uma forma do sistema perceber que há uma grande diferença de trajetórias e reniciar os coeficientes do filtro para que esse nunca se torne oscilante.

O terceiro ponto mais notável que exigirá uma atenção na implementação é a questão de que, exatamente pela oscilação gerada na troca busca de trajetória, o sistema acaba se desestabilizando quando este recebe uma nova trajetória e logo após para de receber novas informações.
Neste caso, o sistema parece entrar em um estado de instabilidade e acaba ficando completamente incontrolável, efetuando diversas rotações até entrar no estado de retorno à posição inicial ou receber novas informações de posição sobre algum alvo (exemplificada aos minutos 6:24 do Apêndice \ref{cap:apendice_troca_sat}).
Em ambos casos, o sistema retorna completamente à estabilidade ao reiniciar os parâmetros do filtro.
Uma alternativa para esse caso seria a de verificar a diferença de posição exigida pelo filtro. Caso essa seja maior que um determinado delta, o sistema entra na rotina de retorno a zero.
É importante salientar que um sistema de verificação já é implementado para a elevação, que não pode atingir valores muito negativos nem muito acima de 90 graus, causando a limpeza dos parâmetros do filtro.
Entretanto, a implementação dessa solução para o azimute se mostra desafiadora, pois a distinção entre um rastreio correto no qual há uma grande aceleração em azimute (como um rastreio próximo do zênite) e uma instabilidade pode ser difícil de prever até o sistema se tornar muito instável e danificar sua estrutura.

No geral, o simulador demonstrou ser uma boa ferramenta para transicionar de um sistema completamente teórico para um sistema físico, permitindo verificar o funcionamento do software embarcado no protótipo e rapidamente iterar e corrigir o código.
